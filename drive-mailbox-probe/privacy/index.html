drive-mailbox-probe — Privacy Policy

Last updated: 2026-10-01

drive-mailbox-probe is a private, owner-operated personal test application run by its owner (contact: leventen@leventen.net) to test, with the owner's own Google account only, how a personal software project can read limited Drive metadata. This policy states what the application can technically do, what it actually does, where information goes, and how long it is kept.

1. Who uses it

One person: the owner, using the owner's Google account. The application is not offered to anyone else, and it collects nothing from any other person.

2. The Google permission requested

Only one permission (OAuth scope) is requested: https://www.googleapis.com/auth/drive.metadata.readonly — "See information about your Google Drive files". Technical scope of that permission: it allows an application to read metadata of files and folders visible to the signed-in account (for example names, types, and sharing and permission information). It does not allow reading file contents, and it does not allow creating, changing, sharing, moving or deleting anything. No other Google permission is requested.

3. What this test actually does (behaviour, as opposed to technical access)

This test deliberately limits itself to far less than the permission allows:

  • Using the owner's consent, it requests only the "capability" flags (yes/no values such as whether the account may rename, share or delete an item) of two named throwaway test items, one test folder and one test file, in a temporary Google shared drive created by the owner for this test.
  • It performs one attempted rename of the test folder, solely to verify that the metadata-only permission refuses it. The attempt is expected to be refused. Afterwards a service account belonging to the owner's own Google Cloud test project (service account A) reads the folder's name to check whether it remained unchanged. The evidence records only whether the name remained unchanged, not the name.
  • It does not list, scan or read any other file, folder or drive through the owner's consent.
  • No Google file content is requested, read or stored. Separately from the owner's consent, the test uses two service accounts in the owner's own Google Cloud test project: service account A, which is used to check the sharing settings of the test items and to exercise the provisioning calls on temporary items it creates itself, and service account B, which only reads and is checked to confirm that it cannot change anything. The owner creates the temporary shared drive and the test items by hand in the Drive interface. Service accounts are not users, and no consent from any other person is involved.

4. What is stored, and where

  • Credentials. The OAuth client configuration and the refresh token issued by Google after the owner approved access, and the two service-account key files, are stored on the owner's own computer, outside the software project folder and excluded from local backups. They are protected at rest by full-disk encryption (Apple FileVault) on the computer's volume and, in addition, are kept inside a strongly encrypted disk image whose passphrase is known only to the owner and which is mounted only while a test command or the local summary step is running (AES-256 encryption, verified on 2026-10-01). The refresh token and OAuth client credentials are used only in the token exchange with Google; the service-account private keys never leave the computer and are used only to sign requests for access tokens.
  • Raw test results. The test writes a machine-readable record of its results inside the same encrypted image. It is not shown to any AI service, GitHub or any other provider, and is deleted during cleanup (section 7). It contains no email addresses and no drive-member identifiers, and never a token, key, file content, response body or file name. It does contain opaque identifiers of the throwaway test items.
  • Review summary and governance record. A local automated step on the owner's computer produces two things from the raw results, using fixed lists of allowed fields, and checks each against the exact addresses, identifiers and credentials known to the test: a temporary review summary kept in the same encrypted image (section 6), and a governance record that contains no result derived from Google API responses. Nothing is shown to anyone else or added to the private repository unless that check passes; if it fails, nothing is shown.

5. Who else processes information, and for what

Apart from Google processing the authentication and API traffic, only the following ever leave the owner's computer, and only after the local check has passed: the governance record, and (subject to the conditions below) the temporary review summary. Neither contains email addresses, member identifiers, Drive item identifiers, credentials, tokens, file names, response bodies or file contents.

  • GitHub stores the governance record in a private, access-controlled repository. As of the date above that repository is private. If its visibility changes, this policy will be updated first and the stored record reviewed before the change. GitHub never receives the review summary or the raw results.
  • AI-assisted development and security-review services, currently Claude by Anthropic and Codex by OpenAI, may process the governance record. They receive the temporary review summary only if the owner has first verified that the account and surface used will not use the material to train generalized models and that its retention there is compatible with the summary's deletion deadline; if either cannot be verified, the summary is not sent to that service and the owner reviews it alone. This processing is solely for operating, testing and securing this application and excludes tokens, credentials, file contents, response bodies and file names. This policy will be updated before a summary or record is sent to a materially different provider.
  • No one else. The operator does not sell this data, does not use it for advertising, and does not use Google user data to create, train or improve a generalized artificial-intelligence or machine-learning model. Information is not transferred or disclosed to any other party, except as required by law, for security purposes such as investigating abuse, or with the owner's own consent.

6. Review summary and governance record — contents and retention

  • Temporary review summary. May contain: dates and times; pass/fail findings for each check; request status and Google's reason values; the permission scope Google reports; capability flags; and aggregate counts and role labels such as "one organizer, one reader". It contains no direct identifiers, file names or file contents, but it does contain minimized results derived from Google API responses, and it is handled under the Limited Use requirements in section 11. It is stored only in the encrypted image, is never added to the repository, and is deleted when the owner finishes the review and in any case no later than 7 days after it is created. No fingerprint of it is kept in the repository.
  • Governance record. Kept in the private repository as a project decision record. It contains only: a probe identifier and date; which gate decision was made; the hashes of non-data documents and code only (the plans, this policy's versions and the tools); the deadlines; and the dates on which cleanup steps, including deletion of the review summary and removal of the encrypted image, were completed. It contains no capability values, Google reason or status results, scope-response values, role aggregates or any other observation derived from Google API responses, so it is not deleted with the credentials in section 7. If any Google user data or identifier were ever committed by mistake, the owner would treat it as an incident and prepare a specific remediation plan; this policy does not promise that any repository history can be erased.

7. Retention of credentials, fixtures and raw results

Each run of the test has its own deadlines. OAuth credentials and temporary Drive fixtures are deleted promptly after phase 2 of the run and no later than 14 days after consent. The two service-account keys are deleted no later than 14 days after they were created, whether or not consent or phase 2 has happened. If phase 2 is not completed in time, the same deletions still occur, the run is recorded as incomplete, and a later attempt is a new run. Starting another run never extends an earlier run: it requires separately created credentials and fixtures and a new clock. Producing a summary never delays any deletion. Deletion covers: the refresh token (revoked at Google) and the OAuth client, the service-account keys, all local copies of those credential files, the raw machine-readable results, the temporary review summary, the encrypted disk image, the temporary shared drive and its test items, and the test project's Google Cloud resources.

8. Revoking access

The owner can revoke the application's access at any time at https://myaccount.google.com/permissions (choose "drive-mailbox-probe", then "Delete all connections"). Revocation prevents future authorization, subject to Google's revocation processing and the remaining lifetime of any access token already issued.

9. Other people and children

The application is not intended for anyone other than its owner, and collects nothing from anyone else.

10. Changes and contact

Changes are posted on this page with a new date. Questions: leventen@leventen.net.

11. Google API Services User Data Policy

drive-mailbox-probe's use and transfer to any other app of information received from Google APIs will adhere to the Google API Services User Data Policy, including the Limited Use requirements.
